영향도 순서로 리뷰하세요. 두 줄 아래에 데이터 레이스가 있는데 네이밍에 리뷰어의 주의력을 쓰지 마세요.

## 1. 정확성

- 변경 사항이 풀 리퀘스트에 적힌 대로 동작하나요? 이를 증명하는 테스트가 있나요?
- 에러 경로가 처리되었나요(`throws`, 빈 상태, 오프라인 네트워킹)?
- 앱 외부에서 들어오는 데이터에 강제 언래핑이나 `try!`를 쓰고 있지는 않나요?

## 2. 동시성과 수명

- UI 업데이트는 `@MainActor`에서 일어납니다.
- 새로 추가된 `Task { }` 블록: 누가 취소하나요? 화면의 수명을 넘어서 `self`를 강하게 캡처하지는 않나요?
- 격리 도메인(isolation domain)을 넘나드는 공유 가변 상태는 `Sendable`이거나 actor로 보호됩니다.
- 저장되는 클로저는 필요한 곳에 `[weak self]`를 사용합니다 — 순환 참조가 없어야 합니다.

## 3. 사용자가 체감하는 품질

- 접근성: 의미 있는 `accessibilityLabel`이 있고, Dynamic Type과 VoiceOver에서 동작합니다.
- 현지화: 사용자에게 보이는 문자열을 하드코딩하지 않고, 복수형은 String Catalog의 variant를 사용합니다.
- 작은 화면, 가로 모드, 가장 큰 글자 크기에서도 레이아웃이 깨지지 않습니다.

## 4. 아키텍처

- 새 코드가 모듈의 기존 패턴(MVVM, 코디네이터, 의존성 주입 방식)을 따릅니다.
- 의존성은 안쪽을 향합니다. Feature 모듈이 다른 Feature 모듈을 import 하지 않습니다.

## 5. 테스트

- 새 로직은 단위 테스트로 커버하고, UI 테스트는 핵심 흐름에만 씁니다.
- 테스트는 결정적(deterministic)이어야 합니다 — 실제 네트워크나 sleep을 쓰지 않고, 시계와 날짜는 주입합니다.

## 6. 스타일

스타일은 린터에 맡기세요. 꼭 코멘트를 남겨야 한다면 `nit:`을 앞에 붙여 작성자가 선택 사항임을 알 수 있게 하세요.
